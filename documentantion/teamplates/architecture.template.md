# Шаблон архитектурной документации

> **Назначение файла:** универсальный шаблон для создания `architecture.md` — актуального описания технической архитектуры проекта.
>
> Этот файл является шаблоном и не содержит информации о конкретном проекте.
>
> При создании `architecture.md` необходимо использовать этот шаблон как структуру и руководство по детализации. Инструкции, вопросы и примеры из этого файла не должны копироваться в `architecture.md`.

---

# 0. Правила заполнения

### Назначение

Определяет общие требования к созданию и поддержанию `architecture.md`.

### Основные правила

1. `architecture.md` описывает **текущее состояние технической системы**.
2. Архитектура должна быть описана независимо от истории её создания.
3. Каждое существенное архитектурное решение должно иметь обоснование.
4. История решений и рассмотренные альтернативы хранятся в ADR.
5. Не следует описывать в `architecture.md` детали реализации отдельных функций, если они не влияют на архитектуру системы.
6. Не следует описывать технологии только ради перечисления используемого стека.
7. Необходимо разделять:

   * обязательные требования;
   * архитектурные решения;
   * технические детали реализации;
   * предположения.
8. Если архитектурное решение ещё не принято, оно не должно быть представлено как принятое.
9. Если существующая реализация отличается от задокументированной архитектуры, документ должен быть приведён в соответствие с фактическим состоянием системы либо расхождение должно быть явно зафиксировано.
10. Архитектура должна отражать **текущую систему**, а не предполагаемое будущее состояние.

### Требование к детализации

Документ должен позволять разработчику или агенту:

* понять устройство системы;
* определить ответственность основных компонентов;
* понять взаимодействие компонентов;
* понять основные потоки данных;
* понять ключевые архитектурные ограничения;
* безопасно вносить изменения, не нарушая существующую архитектуру.

* Какой архитектурный стиль используется?

```text

    ↓
Клиентское приложение
    ↓

    ↓
```

Раздел должен позволять получить общее понимание архитектуры без изучения всех последующих разделов.

Не следует перечислять здесь все компоненты системы.

# 2. Архитектурные требования и ограничения

### Назначение

Зафиксировать условия, которые влияют на архитектурные решения.

### Вопросы

* Какие требования продукта влияют на архитектуру?
* Какие ограничения существуют?
* Есть ли требования к производительности?
* Есть ли требования к безопасности?
* Есть ли требования к доступности?
* Есть ли ограничения по бюджету?
* Есть ли ограничения инфраструктуры?
* Есть ли ограничения внешних систем?
* Есть ли ограничения команды или процесса разработки?

### Пример

> Система должна поддерживать работу пользователей с мобильных устройств.
>

### Требование к детализации

Указывать только требования и ограничения, которые действительно влияют на архитектуру.

# 3. Границы системы

### Назначение

Определить, что относится к системе, а что находится за её пределами.

### Вопросы

* Что является частью системы?
* Какие внешние системы существуют?
* Кто или что взаимодействует с системой?
* Где проходят границы ответственности?
* Какие данные поступают извне?
* Какие данные система передаёт наружу?

### Пример

```text
[Пользователь]
      │
      ▼
┌───────────────────┐
│      Система      │
│                   │
│  Client → API     │
│          ↓        │
│       Database    │
└───────────────────┘
      │
      ▼
[Внешний сервис]
```

### Требование к детализации

Границы должны быть достаточно понятны, чтобы определить, какая система отвечает за конкретную операцию или данные.

# 4. Архитектурный стиль

### Назначение

Зафиксировать общий способ организации системы.

### Вопросы

* Какой архитектурный подход используется?
* Как система разделена на части?
* Как организована зависимость между частями?
* Где находятся границы модулей?
* Какие архитектурные принципы используются?
* Какие архитектурные подходы сознательно не используются?

### Пример

> Система построена как модульный монолит. Функциональные области разделены на независимые модули с явно определёнными границами взаимодействия.

### Требование к детализации

Недостаточно назвать архитектурный стиль.

Необходимо описать, **как выбранный стиль применяется именно в системе**.

# 5. Компоненты системы

### Назначение

Описать основные технические компоненты системы.

### Вопросы

* Какие компоненты существуют?
* За что отвечает каждый компонент?
* Какие зависимости между компонентами существуют?
* Какие компоненты являются критическими?
* Какие компоненты являются внешними?

### Структура

Для каждого значимого компонента:

```md
### Название компонента

Назначение:
...

Ответственность:
...

Зависимости:
...

Граница ответственности:
...
```

### Пример

```md
### API

Назначение:
Предоставляет интерфейс взаимодействия между клиентом и серверной частью системы.

Ответственность:
- обработка запросов;
- валидация входных данных;
- авторизация;
- передача данных в соответствующие модули.

Не отвечает за:
- отображение пользовательского интерфейса;
- хранение клиентского состояния.
```

### Требование к детализации

Описывать архитектурно значимые компоненты.

Не следует превращать раздел в список каждого файла или класса проекта.

# 20. ADR

### Назначение

Предоставить индекс архитектурных решений проекта.

### Структура

```md
| ID | Решение | Статус |
|----|---------|--------|
| ADR-001 | ... | Accepted |
| ADR-002 | ... | Superseded |
```

### Требование к детализации

Не дублировать содержимое ADR.

`architecture.md` должен позволять быстро понять, какие архитектурные решения существуют и где находится их история.

# 21. Открытые вопросы

### Назначение

Собрать архитектурные решения, которые ещё не определены.

### Статусы

* `open` — решение отсутствует;
* `decided` — решение принято;
* `rejected` — вариант рассмотрен и отклонён.

### Формат

```md
### [open] Название вопроса

Вопрос:
...

Контекст:
...

Что необходимо определить:
...
```

### Требование к детализации

Открытый вопрос должен быть сформулирован таким образом, чтобы его можно было передать ответственному человеку для принятия решения.

Не следует использовать этот раздел как список случайных технических мыслей.

### Вопросы

* Какие архитектурные ограничения уже существуют?
* Какие компромиссы были сознательно приняты?
* Какие части системы требуют дальнейшего улучшения?
* Какие ограничения нельзя нарушать?
* Какие ограничения являются временными?

### Пример

> Текущая архитектура рассчитана на объём нагрузки MVP и не предусматривает горизонтальное масштабирование отдельных компонентов.

### Требование к детализации

Не скрывать известные ограничения.

Ограничение должно быть описано достаточно конкретно, чтобы агент не принял его за случайную особенность реализации.

# Правила для агента

При создании или обновлении `architecture.md` агент должен:

1. Сначала ознакомиться с этим шаблоном.
2. Изучить `product.md`, существующий код и доступную техническую документацию.
3. Если `architecture.md` отсутствует — создать его на основании фактического состояния проекта и известных требований.
4. Если `architecture.md` существует — сначала прочитать его и обновлять только затронутые разделы.
5. Не описывать предполагаемую архитектуру как существующую.
6. При анализе существующего проекта отдавать приоритет фактическому состоянию кода и инфраструктуры.
7. Не придумывать технологии, компоненты или архитектурные ограничения, которых нет в проекте.
8. Отделять архитектурные решения от деталей реализации.
9. Для существенных новых архитектурных решений создавать или предлагать ADR.
10. Не изменять существующее архитектурное решение только для того, чтобы сделать реализацию задачи удобнее, если это не является частью задачи.
11. Если реализация противоречит `architecture.md`, определить, что является актуальным:

    * если архитектура изменилась намеренно — обновить `architecture.md` и соответствующий ADR;
    * если реализация ошибочна — исправить реализацию;
    * если невозможно определить актуальное состояние — добавить открытый вопрос.
12. Не удалять существующие архитектурные решения без основания.
13. Не добавлять в документ подробности, которые относятся к отдельной функциональной спецификации.
14. Не использовать `architecture.md` как журнал изменений. История решений хранится в ADR.
15. Если архитектурного решения ещё нет, не принимать его самостоятельно, если оно требует продуктового или архитектурного выбора пользователя.

# Связь с architecture.md

`architecture.md` является актуальным описанием архитектуры проекта.

Он должен ссылаться на этот шаблон:

```md
> Структура и правила заполнения документа определяются [architecture.template.md](./templates/architecture.template.md).
```

`architecture.md` не должен содержать инструкции, вопросы и примеры из шаблона.

В нём должны находиться только сведения о текущем состоянии архитектуры конкретного проекта.

История существенных архитектурных решений хранится отдельно в ADR.
