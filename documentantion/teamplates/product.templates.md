# Шаблон продуктовой документации

> **Назначение файла:** универсальный шаблон для создания `./documentation/product.md` — актуального описания продукта.
>
> Этот файл является шаблоном и не содержит информации о конкретном проекте.
>
> При создании `./documentation/product.md` необходимо использовать этот шаблон как структуру и руководство по детализации. Не следует копировать в `./documentation/product.md` инструкции, вопросы и примеры из этого файла.

---

## 0. Правила заполнения

### Назначение

Определяет общие требования к созданию `./documentation/product.md`.

### Правила

1. `./documentation/product.md` должен описывать **что представляет собой продукт, какую проблему он решает, для кого он предназначен и как должен работать**.
2. Документ должен описывать продукт независимо от конкретного технологического стека.
3. Не следует описывать в `./documentation/product.md` техническую реализацию, если она не является непосредственным ограничением продукта.
4. Не следует добавлять предположения как факты.
5. Если информация неизвестна, необходимо явно указать это в разделе «Открытые вопросы».
6. Если решение принято, оно должно быть отражено в соответствующем разделе, а не оставлено только в обсуждениях, Issue или переписке.
7. Документ должен отражать **текущее состояние продукта**, а не всю историю его развития.
8. Изменения продукта должны приводить к обновлению соответствующих разделов `product.md`.

### Требование к детализации

Документ должен быть достаточно подробным, чтобы новый разработчик или агент, не знакомый с проектом, мог понять продукт и его основные требования без изучения всей истории проекта.

При этом документ не должен превращаться в техническое задание на каждую отдельную функцию.

# 1. Обзор продукта

### Назначение

Дать краткое целостное представление о продукте.

### Вопросы

* Что представляет собой продукт?
* Для кого он предназначен?
* Какую основную ценность предоставляет?
* Что пользователь может сделать с помощью продукта?
* Чем продукт принципиально отличается от альтернатив?

### Пример

> Сервис позволяет пользователям находить специалистов для выполнения небольших бытовых задач и быстро договариваться с ними о выполнении работы.

### Требование к детализации

Раздел должен позволять понять суть продукта за несколько предложений.

Не следует описывать здесь архитектуру, используемые технологии или полный список функций.

# 2. Проблема

### Назначение

Зафиксировать проблему, ради решения которой существует продукт.

Проблема должна быть сформулирована независимо от предлагаемого решения.

### Вопросы

* Какую проблему испытывают пользователи?
* Кто именно испытывает эту проблему?
* В каком контексте она возникает?
* Как пользователи решают её сейчас?
* Почему существующие способы решения недостаточны?
* Насколько проблема значима?
* Какие есть основания считать проблему реальной?

### Пример

> Пользователю сложно быстро найти исполнителя для небольшой разовой задачи. Существующие сервисы ориентированы преимущественно на крупные заказы и требуют длительного процесса поиска и выбора исполнителя.

### Требование к детализации

Должно быть понятно:

1. кто испытывает проблему;
2. в чём она заключается;
3. почему она имеет значение.

Не следует описывать решение проблемы в этом разделе.

---

# 3. Целевые пользователи

### Назначение

Определить группы пользователей, для которых создаётся продукт.

### Вопросы

* Кто является основным пользователем?
* Какие существуют вторичные группы пользователей?
* Какие характеристики существенно влияют на использование продукта?
* Какие задачи пользователь пытается решить?
* В каком контексте пользователь взаимодействует с продуктом?

### Пример

> Основная группа — люди, которым периодически требуется помощь с небольшими бытовыми задачами.
>
> Вторичная группа — исполнители, которые хотят получать дополнительные заказы без необходимости самостоятельно искать клиентов.

### Требование к детализации

Не следует ограничиваться демографическими характеристиками.

Важнее описать поведение, потребности, контекст и мотивацию пользователя.

# 4. Потребности пользователей

### Назначение

Определить, какие задачи и потребности пользователь хочет закрыть с помощью продукта.

### Вопросы

* Что пользователь хочет сделать?
* Какого результата он хочет достичь?
* Что мешает ему достичь результата сейчас?
* Что является для него наиболее важным?
* Какие действия являются критическими для достижения результата?

### Пример

> Пользователь хочет быстро сравнить доступных исполнителей и выбрать подходящего без необходимости самостоятельно связываться с несколькими людьми.

### Требование к детализации

Потребность должна описываться через пользовательский результат, а не через функцию интерфейса.

Плохо:

> Пользователю нужна кнопка «Найти исполнителя».

Хорошо:

> Пользователь хочет быстро найти подходящего исполнителя.

# 5. Цели продукта

### Назначение

Зафиксировать, каких результатов должен достичь продукт.

### Вопросы

* Какого результата должен достичь продукт?
* Какие пользовательские проблемы необходимо решить в первую очередь?
* Какие бизнес- или продуктовые результаты являются приоритетными?
* Какие цели относятся к MVP?
* Какие цели относятся к будущим версиям?

### Пример

> Основная цель MVP — проверить, готовы ли пользователи размещать задачи и выбирать исполнителей через платформу.

### Требование к детализации

Цели должны быть конкретными и проверяемыми настолько, насколько это возможно.

Не следует смешивать цели продукта с техническими задачами.

# 6. Границы продукта


## Назначение

Зафиксировать, что входит в текущий объём продукта, а что сознательно не входит.

Вопросы
Какие возможности обязательны для текущей версии?
Какие возможности запланированы, но отложены?
Какие возможности сознательно исключены?
Что является частью MVP?
Какие идеи не относятся к текущему продукту?
Структура
Входит в продукт

Перечислить возможности, необходимые для текущей версии.

Не входит в продукт

Перечислить возможности, которые не должны реализовываться в рамках текущей версии.

Пример

В MVP входит создание задачи, поиск исполнителя, отклик исполнителя и завершение заказа.

В MVP не входит автоматическое распределение заказов и система рекомендаций.

Требование к детализации

Границы должны быть достаточно однозначными, чтобы разработчик или агент мог определить, является ли конкретная задача частью текущего продукта.

# 7. Основные пользовательские сценарии

## Назначение

Описать ключевые пути пользователя через продукт.

Вопросы
Как пользователь начинает взаимодействие с продуктом?
Какой результат он хочет получить?
Какие основные шаги проходит?
Какие существуют альтернативные пути?
Что происходит при успешном завершении сценария?
Что происходит при ошибке или невозможности продолжить?
Пример
Пользователь
→ открывает продукт
→ создаёт задачу
→ получает отклики
→ выбирает исполнителя
→ подтверждает выполнение
→ завершает заказ
Требование к детализации

Описывать необходимо прежде всего пользовательское поведение и результат, а не конкретные элементы интерфейса.

Для сложных сценариев допускается отдельная спецификация.

# 8. Функциональные требования

## Назначение

Зафиксировать, какие возможности должен предоставлять продукт.

Вопросы
Что пользователь должен иметь возможность сделать?
Какие действия доступны каждой роли?
Какие данные можно создавать, изменять и удалять?
Какие состояния существуют?
Какие ограничения существуют для действий?
Какие действия требуют авторизации?
Пример

Авторизованный пользователь может создать объявление.

Пользователь может изменить собственное объявление до момента получения первой ставки.

Пользователь не может изменять чужое объявление.

Требование к детализации

Требования должны описывать наблюдаемое поведение системы.

Избегать формулировок вроде:

«Реализовать компонент формы».

Это техническая задача, а не функциональное требование.

# 9. Бизнес-правила

## Назначение

Зафиксировать правила предметной области, которые должны соблюдаться независимо от интерфейса и реализации.

Вопросы
Какие действия разрешены?
Какие действия запрещены?
При каких условиях изменяется состояние сущности?
Какие ограничения существуют?
Какие правила связаны с ролями пользователей?
Какие правила связаны со временем, деньгами, статусами или другими доменными условиями?
Пример

Пользователь не может сделать ставку ниже или равную текущей максимальной ставке.

После завершения аукциона новые ставки принимать нельзя.

Требование к детализации

Бизнес-правила должны быть сформулированы однозначно.

Если правило влияет на несколько частей системы, оно должно быть описано здесь, а не только в отдельной реализации.

# 10. Сущности и терминология

## Назначение

Зафиксировать основные понятия продукта и единообразную терминологию.

Вопросы
Какие основные сущности существуют?
Как называются эти сущности?
Как они связаны между собой?
Какие термины имеют специальное значение?
Какие названия нельзя использовать как синонимы?
Пример

Лот — конкретный товар, выставленный на аукцион.

Требование к детализации

Если термин имеет специальное значение в продукте, оно должно быть определено здесь.

Терминология должна использоваться одинаково в интерфейсе, коде, документации и коммуникации команды.

Вопросы

Какие требования существуют к доступности?

# 17. Открытые вопросы

## Назначение

Собрать информацию, которая пока не определена и требует решения.

Формат

Каждый вопрос должен иметь статус:

open — решение отсутствует;
decided — решение принято и должно быть отражено в соответствующем разделе;
rejected — вариант рассмотрен и сознательно отклонён.
Структура
### [open] Название вопроса

Вопрос:
...

Контекст:
...

Что необходимо определить:
...
Пример
### [open] Ограничение количества ставок

Вопрос:
Должно ли существовать ограничение на количество ставок одного пользователя?

Контекст:
Необходимо определить правила поведения пользователя при активном аукционе.

Что необходимо определить:
Максимальное количество ставок и условия ограничения.
Требование к детализации

Открытый вопрос должен быть сформулирован так, чтобы его можно было передать ответственному человеку для принятия решения.

Нельзя использовать раздел как список неопределённых мыслей.

# 18. Связанные документы

## Назначение

Указать документы, которые являются источниками дополнительного контекста.

Возможные ссылки
техническая архитектура;
архитектурные решения (ADR);
спецификации отдельных функций;
дизайн;
API-документация;
аналитика;
исследования пользователей.
Требование к детализации

Ссылаться только на существующие и актуальные документы.

Правила для агента

При создании или обновлении product.md агент должен:

Сначала ознакомиться с этим шаблоном.
Изучить доступные требования, Issue, брифы, исследования и существующую документацию проекта.
Не придумывать отсутствующую информацию.
Отделять подтверждённые требования от предположений.
Если информации недостаточно для заполнения важного раздела — задать уточняющий вопрос или добавить его в «Открытые вопросы».
Не переносить в product.md технические решения, которые относятся к архитектуре.
Не создавать требования только потому, что они являются распространённой практикой.
При изменении продукта обновлять соответствующий раздел product.md.

Не изменять структуру этого шаблона без явной необходимости.
Связь с product.md

Он должен ссылаться на этот шаблон:

> Структура и правила заполнения документа определяются [product.template.md](.documentation/templates/product.template.md).

product.md не должен содержать инструкции, вопросы и примеры из шаблона. В нём должны находиться только конкретные решения, требования и знания о текущем проекте.
